## 0. Решения по разделу 4 фидбека (с обоснованием)

### D1 — Конверты vs Goals: **одна сущность `envelopes`, заменяет `goals`**

`goals` — leaf-таблица (на неё нет ни одного FK), по итогам dogfood'a — мёртвая фича.
Конверт (pay-yourself-first) — драйвер v1. Семантически конверт ⊇ цель: у конверта
может быть необязательная цель (сумма/дата). Поэтому **сливаем в одну сущность**,
переосмысленную вокруг конверта, а не цели.

Модель `envelopes` (мигрируем из `goals`):
- `percent` (nullable, `0 < percent <= 100`) — доля каждого подтверждённого дохода,
  которую конверт автоматически отщипывает. `NULL` = ручной конверт (без авто-скима).
- `target_amount_minor` → **становится nullable** (не у каждого конверта есть цель).
- `target_date` (nullable) — сохраняем.
- **Убираем `linked_account_id`** — «прогресс = баланс целого счёта» это другая (и
  путаная) семантика. Конверт — виртуальный срез *общего* баланса, не отдельный счёт.

Накопленное в конверте — **event-sourced** через леджер `envelope_entries`
(см. [ADR-0007](./adr/0007-envelopes.md)), консистентно с [ADR-0004](./adr/0004-event-sourced-balances.md):
```
envelope_entries(id, envelope_id, workspace_id, amount_minor signed,
                 kind('skim'|'manual'|'withdraw'),
                 source_transaction_id?, created_by_user_id, created_at)
envelope.reserved_minor = Σ amount_minor
```
**`workspace_id` денормализован на `envelope_entries`** (must-fix): иначе изоляция
обходится через дочернюю таблицу (запрос entries фильтруется только join'ом через
`envelopes` — класс «забыл guard → утечка»). Единый scope-ключ на каждой владеемой
таблице, как и везде.

Почему леджер, а не колонка `reserved_minor`: `percent` меняется со временем, но сумма
скима должна быть **заморожена** на момент дохода → каждый ским всё равно надо
персистить строкой. Колонка-агрегат дрейфовала бы; леджер — нет.

Ським-триггер: при подтверждении транзакции `kind='income'` для каждого **активного
конверта** (`archived_at IS NULL AND percent IS NOT NULL`) вставляем `skim`-строку
= `floor(income.amount_minor * percent / 100)`, в **той же БД-транзакции**, что и сам
income. **floor**, чтобы никогда не зарезервировать больше дохода. `kind='adjustment'`
(даже с `to_account_id` — это inflow по балансу) **доходом не считается, не скимится**.
Сумма всех `percent` не ограничена 100% на уровне БД (юзер сам отвечает); Σ>100% — UI
предупреждает.

**PIN (default, подтвердить):** архивный конверт **исключается из суммы reserved через
query-filter** (`reserved = Σ entries по конвертам WHERE archived_at IS NULL`), НЕ через
компенсирующую entry — леджер остаётся неизменяемым, un-archive восстанавливает резерв
без правки истории (pass-2 B2). Деньги при архивации виртуально возвращаются в «доступно».

«Доступно к трате» = `Σ балансы счетов − Σ reserved по конвертам`.

### D2 — Budgets: **в backlog**

`budgets` (лимиты трат на категорию) ≠ конверты (резервирование дохода). В
done-criteria budgets не упомянуты ни разу. Прогноз планирования покрывает
forward-looking «не перетрачу ли»; ретроспективные cap'ы — это фича, которую
просят, но не используют (dogfood уже показал ненужность аналитики, budgets рядом).

Решение: **таблицу, роутер и 34 теста оставляем** (рабочий код не выбрасываем),
**UI не делаем, схему не расширяем**. Инертный backend. Пересмотр после v1, если
появится реальная боль. При re-key (Phase 4) `budgets.user_id → workspace_id` —
едет вместе со всеми, чтобы не оставлять полу-мигрированную таблицу.

### D3 — Формула прогноза баланса

```
available_now        = Σ балансы всех счетов workspace (сейчас, event-sourced)
reserved             = Σ reserved по активным конвертам workspace
planned_income       = Σ planned_operations(kind=income,  status='planned'),
                         все вхождения в окне (today, horizon]
planned_expense      = Σ planned_operations(kind=expense, status='planned'),
                         все вхождения в окне (today, horizon]

projected_balance    = available_now + planned_income − planned_expense
projected_available  = projected_balance − reserved      ← заголовок «к концу N»
```

Пины:
- `horizon` по умолчанию — конец текущего месяца; параметризуем. «Конец месяца» =
  `date(y, m, last_day)`, окно `(today, horizon]` (today исключён слева, последний день
  включён). `today` = `datetime.now(timezone.utc).date()` — **тот же источник, что
  `goals.py:143`**, чтобы прогноз и остальное приложение сходились в «сегодня».
- Считаем **только `status='planned'`**. Подтверждённый план уже стал транзакцией →
  сидит в `available_now`; учитывать его в planned_* = двойной счёт.
- **Рекуррентные + partial-confirmed (must-fix):** `occurrences()` стартует не с
  `first_date`, а с `first_date + completed_cycles * period` — со **следующего
  неподтверждённого** вхождения. Иначе досрочно подтверждённое вхождение (особенно
  `recurrence='week'`) всё ещё считается планом → двойной счёт. Развёртка внутри окна,
  не дальше `remaining_cycles = total_cycles − completed_cycles`.
- **`next_occurrence` не хранится** (must-fix): выводится как `first_date +
  completed_cycles * period`. Единственный источник истины — `completed_cycles`; confirm
  «двигает» вхождение инкрементом счётчика, не записью в отдельную колонку.
- **v1-упрощение:** будущие скимы конвертов из *запланированного* дохода НЕ
  моделируем (иначе рекурсия). `reserved` = текущий баланс конвертов. Зафиксировано.
- **Психология (UI, не формула):** `projected_available > 0` → «Излишек N — в конверт?»;
  `<= 0` → мягкая формулировка, не красный приговор. Формула честная, переобрамляет подача.

См. [ADR-0008](./adr/0008-planning-forecast.md).

### D4 — Совместный аккаунт: **workspace-scoping** (вариант «б», переименован)

Сейчас владение всем键ится на `user_id` напрямую. Вариант (а) `shared_account_group_id`
на счетах — слишком узкий: шарить надо и транзакции, и категории, и конверты, и планы,
а не только счета; group_id, размазанный по всем таблицам, неоднозначен и течёт.

Решение — единый scope-ключ. Вводим:
- `workspaces(id, name, kind('personal'|'shared'), created_at)`
- `workspace_members(workspace_id, user_id, role, joined_at, unique(workspace_id,user_id))`
- **re-key** владеемых таблиц `user_id → workspace_id`. **Phase 4 мигрирует только 6
  существующих** таблиц: `accounts, transactions, categories, budgets, goals, receipts`.
  `planned_operations` (Phase 5) и `envelopes`/`envelope_entries` (Phase 6) **рождаются
  workspace-native** — не мигрируются повторно (это и есть выгода foundation-first).
- `users.active_workspace_id` (FK, `ON DELETE SET NULL` — удаление workspace не должно
  удалять юзера) — текущий выбранный scope; переключение = PATCH **с проверкой
  membership перед записью** (см. Auth ниже).
- На провизионинге каждому юзеру — personal workspace (`role='owner'`) + 2 дефолтных
  счёта в нём.

Имя **`workspace`**, не «household»/«account» — чтобы не коллидить с финансовым
«счёт/account».

`workspaces.kind` — **инвариант, не просто label** (must-fix consistency): приглашения
разрешены только на `kind='shared'`; personal нельзя расшарить (нет invite-эндпоинта).
Не даём `kind` разъехаться с member-count.

Auth (must-fix — закрыть дыру полностью, в два слоя):
- `current_workspace` **ре-валидирует membership на КАЖДОМ запросе** (не доверяет
  сохранённому `active_workspace_id`): резолв id → проверка, что текущий юзер член →
  не член → 403.
- Switch-PATCH `active_workspace_id` **проверяет membership ДО записи**: иначе юзер
  выставит чужой workspace и все последующие `WHERE workspace_id=...` пройдут. Тест
  `test_switch_to_non_member_workspace_403`.
- Все запросы ресурсов `WHERE workspace_id = current_workspace.id`; cross-resource →
  cross-workspace 404 (копируем cross-tenant guard из `transactions.py`).

**Без каскадного удаления:** удаление юзера убирает его строки `workspace_members`,
но НЕ shared workspace (он键ится на `workspace_id`, не на `user_id`). Personal
workspace архивируется вместе с юзером. Аудит — `created_by_user_id` (nullable,
`ON DELETE SET NULL`) на мутациях + таблица `audit_log` для «кто/что/когда».
Приглашения — `workspace_invites` (token → Telegram-ссылка → accept). v1: shared ≤ 2.

См. [ADR-0009](./adr/0009-workspace-multiuser.md). **Это самая тяжёлая и рискованная
часть всего плана** (re-key трогает каждую таблицу; cross-tenant баги становятся
cross-workspace утечками). Фокус plan-reviewer — сюда.

## 1. Пушбэк по порядку фаз

Фидбек предлагает: планирование → конверты → multi-user → дизайн.

**Возражаю по сиквенсу.** Если строить планирование и конверты на `user_id`, а потом
re-key'ить в `workspace_id`, получаем: (1) бóльшую миграцию (на 2 таблицы больше),
(2) ретрофит cross-workspace auth в 2 новых роутера, (3) построение фич «дважды».

Подсчёт работы:
- **foundation-first** (re-key до фич): мигрировать 5 таблиц + ретрофит 7 роутеров,
  потом 2 фичи строятся workspace-native начисто.
- **feature-first** (re-key последним): построить 2 фичи на `user_id`, потом
  мигрировать 7 таблиц + ретрофит 9 роутеров.

Foundation-first — строго меньше работы и меньше риска (меньшая миграция; security-
critical паттерн изоляции устанавливается один раз и копируется в новые фичи, а не
ретрофитится). Цена: фаза foundation не даёт видимой ценности.

**Компромисс:** разбиваю multi-user на (а) **foundation** — re-key + workspace-auth,
невидимая инфра, рано; (б) **sharing** — приглашения/аудит/переключатель, видимая
фича, позже. Тяжёлая-но-невидимая миграция изолирована; видимый шеринг — отдельный
value-stop. Плюс quick-add идёт первым как дешёвый value-win.

Рекомендованный порядок (если не согласен — вернёмся к feature-first, скажи):

| Phase | Что | Done-criteria | Риск |
|---|---|---|---|
| 3 | Quick-add ≤3 тапа | #2 | низкий |
| 4 | Workspace foundation (re-key, без UI) | (инфра под #1) | **высокий** |
| 5 | Планирование + прогноз (+ подкатегории) | #3 | средний |
| 6 | Конверты (pay-yourself-first) | #4 | средний |
| 7 | Sharing + регистрация + удаление | #1 | высокий |
| 8 | Дизайн-рефреш | #5 | средний |
| 9 | FINAL GATE — 2 недели использования | #6 | — |

Каждая фаза заканчивается pause point (паттерн из 3b сохранён).

## Phase 4 — Workspace foundation (re-key, инфра) — **высокий риск**

Невидимая снаружи фаза: приложение остаётся одно-пользовательским, но владение
переезжает с `user_id` на `workspace_id`. Делается один раз, в изоляции, с упором
на тесты cross-workspace изоляции.

**Миграция (Alembic, ручная — autogenerate не покроет re-key + data backfill). Делается
в один проход без конкурентного трафика — деплой = короткий downtime; бэкап БД до.**
1. `workspaces`, `workspace_members` (новые таблицы). FK: `workspace_members.workspace_id
   → ON DELETE CASCADE` (удалили workspace → ушли членства); `workspace_members.user_id
   → ON DELETE CASCADE` (удалили юзера → ушло его членство, безопасно).
2. **CASCADE-ловушка (must-fix): дропнуть старые `<table>_user_id_fkey` ДО backfill.**
   Все 6 таблиц имеют `ForeignKey("users.id", ondelete="CASCADE")`. Пока старая колонка
   жива, удаление юзера каскадом снесёт уже расшаренные строки. Снимаем FK первым шагом.
3. Backfill: для каждого `users` → personal workspace + membership (`role='owner'`).
4. Добавить `workspace_id` на 6 таблиц (`accounts, transactions, categories, budgets,
   goals, receipts`). Backfill из `user_id` через membership. **Новый FK `workspace_id
   → workspaces.id` БЕЗ `ON DELETE CASCADE`** (`RESTRICT`/`NO ACTION`) — workspace с
   данными нельзя удалить мимо архивации; «без каскада» из D4 держится именно здесь.
5. Системные категории (`user_id IS NULL`) → `workspace_id IS NULL` (глобальные).
6. Переписать partial unique (pass-2 C4 — **COALESCE только там, где нужно**):
   - `categories_user_name_uq` → `categories_ws_name_uq` на `COALESCE(workspace_id,0)`
     (system-категории остаются `workspace_id IS NULL` → нужен COALESCE).
   - `accounts_user_name_uq`, `budgets_active_uq` → плоские `(workspace_id, ...)` **БЕЗ
     COALESCE** (`workspace_id` там `NOT NULL`). Плоскими они и были — оставить плоскими,
     иначе `on_conflict_do_nothing(index_elements=[...])` в provisioning не сматчит
     expression-индекс.
   - `*_user_active_idx` → `*_ws_active_idx`.
7. `users.active_workspace_id` FK `ON DELETE SET NULL` (= personal на старте).
8. Drop старых `user_id` колонок и индексов **после** backfill (FK уже снят на шаге 2).
9. `created_by_user_id` (nullable, `ON DELETE SET NULL`) на `transactions`, `accounts`
   (фундамент аудита; заполнять с Phase 7, колонку заводим тут чтобы не плодить миграции).
   **Pre-sharing строки (P4–P6) имеют `created_by_user_id = NULL` — ожидаемо**, в этом
   окне приложение ещё одно-пользовательское, актор не пишется.

**Auth-рефактор:** `app/auth/deps.py` — добавить `current_workspace` (резолв через
`users.active_workspace_id` + **ре-валидация membership каждый запрос**; 403 если не
член). Switch-PATCH проверяет membership ДО записи (тест `test_switch_to_non_member...`).
Все роутеры (`accounts/categories/transactions/budgets/goals/reports/me`) — фильтр
`WHERE workspace_id = current_workspace.id`, cross-resource → 404. `user_provisioning`
— создаёт personal workspace + membership + 2 счёта идемпотентно; **re-point
`on_conflict_do_nothing(index_elements=["workspace_id","name"], index_where=archived_at
IS NULL)`** (было `["user_id","name"]`, `user_provisioning.py:71-74`) + обновить
регресс-тест `test_on_conflict_with_partial_index_works` (pass-2 C5 — иначе теряется
`index_where` → `InvalidColumnReference` runtime).

**Тесты (критично):**
- `test_workspace_isolation`: юзер A не видит/не мутирует ресурсы workspace B (404).
- `test_switch_to_non_member_workspace_403`: PATCH `active_workspace_id` на чужой
  workspace отклонён до записи (must-fix #8).
- `test_provisioning_creates_personal_workspace` (идемпотентно).
- `test_system_categories_global` (`workspace_id IS NULL` видны всем).
- Регресс: все существующие 129 тестов зелёные после re-key (переписать фикстуры
  `provisioned_user` → отдавать `workspace_id`).
- `test_migration_backfill` (`@no_rollback`): на снапшоте старой схемы — после upgrade
  все строки имеют корректный `workspace_id`.

**Commits:** `feat(backend): workspaces + members tables`,
`feat(backend): re-key owned tables user_id→workspace_id (migration + backfill)`,
`refactor(backend): current_workspace auth scope`. Deploy (миграция на VPS — бэкап БД до!).

## Phase 5 — Планирование + прогноз (DC#3)

Новая сущность (не переиспользуем budgets/goals). Подкатегории — здесь же (планирование
требует детализации, finding #5).

**5.0 Подкатегории:** `categories.parent_id` (nullable FK → categories, `ON DELETE RESTRICT`),
глубина 2. **Инвариант глубины — не CHECK** (must-fix #7): CHECK не видит другую строку.
Enforce в `_validate_*_ref`: если `parent_id IS NOT NULL`, родитель обязан иметь
`parent_id IS NULL` (внук → 422). Тест `test_subcategory_grandchild_rejected`. БД глубину
не гарантирует — задокументировать (bulk insert/миграция могут нарушить). **Архивация
родителя с активными детьми** — сначала архивируем/переносим детей (или запрет 409);
зафиксировать семантику в роутере. Селектор в Add/Plan показывает дерево 2 уровня.
Системные категории без принудительных подкатегорий.

**5.1 `planned_operations`** (см. [ADR-0008](./adr/0008-planning-forecast.md)):
```
planned_operations(id, workspace_id, kind('income'|'expense'),
  amount_minor>0, category_id?, account_id (источник/назначение),
  first_date, recurrence('once'|'week'|'month'|'year'), total_cycles?,
  completed_cycles default 0, status('planned'|'paused'|'done'),
  note?, created_by_user_id, created_at, archived_at?)
```
`next_occurrence` **не колонка** — выводится `nth_occurrence(plan, completed_cycles)`
(must-fix #6). CRUD + cross-workspace guards (`_validate_*_ref` mirrors). Развёртка:
`occurrences(plan, from, to)` старт со **следующего неподтверждённого** вхождения =
`nth_occurrence(...)` — шаг **календарный** (`relativedelta` для month/year, не timedelta;
`once`→`[]` если `completed_cycles>=1`), month-on-31 клампится на конец месяца. Полные
кейсы — в [ADR-0008](./adr/0008-planning-forecast.md) (pass-2 A1).

**5.2 Подтверждение:** `POST /api/planned/{id}/confirm` → создаёт реальную транзакцию
из плана + `completed_cycles += 1` (это и «двигает» следующее вхождение); циклы
исчерпаны → `status='done'`. **Идемпотентность (must-fix #3):** на `transactions` —

## Phase 6 — Конверты pay-yourself-first (DC#4)

**6.1 Миграция goals→envelopes:** **rename** таблицы (P4-era индексы `goals_ws_active_idx`

использовался только goal-progress'ом → ретайр вместе с роутером.

**6.2 Ським-на-доход:** в `transactions` POST при `kind='income'` (и при confirm
плана-дохода) — для каждого **активного** конверта (`archived_at IS NULL AND percent
IS NOT NULL`) вставить `skim`-entry = `floor(amount*pct/100)`, `source_transaction_id`
= id дохода, **в одной БД-транзакции** с income (единый сервис `services/envelopes.py:
skim_on_income`, чтобы POST и confirm не разъехались). **`adjustment` доходом НЕ
считается** (must-fix #4). Ручные `manual`/`withdraw` — `POST /api/envelopes/{id}/entries`.

**6.3 «Доступно к трате»:** `GET /api/envelopes` отдаёт `reserved_minor` (Σ entries) на

**освобождает резерв** (PIN из D1).

**Тесты:** ским = floor(pct), заморожен при смене percent, Σ entries = reserved,
income без активных конвертов → нет entries, **adjustment не скимится**, withdraw
уменьшает, available = Σbal − Σreserved, **архивный конверт не вычитается**,
cross-workspace 404 (в т.ч. через entries-эндпоинт).

## Phase 7 — Sharing + регистрация + удаление (DC#1)

Видимая multi-user фича поверх foundation из Phase 4.

**7.1 Приглашения:** `workspace_invites(id, workspace_id, token, created_by_user_id,
status('pending'|'accepted'|'revoked'|'expired'), expires_at, accepted_by_user_id?, created_at)`.
`POST /api/workspaces/{id}/invites` **только для `kind='shared'`** (на personal —
403; consistency #5) → token → Telegram share-ссылка (deep-link в Mini App).
`POST /api/invites/{token}/accept` → membership (cap: shared ≤ 2; 3-й → 409). revoke/expire.
- **Token:** `secrets.token_urlsafe(32)` (≈43 симв) — влезает в Telegram `startapp`
  (лимит ~64). **TTL `expires_at` = +7 дней** (для двоих с запасом).

**7.2 Shared workspace:** `POST /api/workspaces` (kind='shared'), переключатель активного
workspace в UI (Меню/Настройки) — PATCH с membership-guard (см. Phase 4 Auth). Оба
участника — root.

**7.3 Аудит:** `audit_log(id, workspace_id, actor_user_id, entity_type, entity_id,
action('create'|'update'|'delete'), snapshot_json, created_at)`. Логируем create/update/delete
на `transactions` + `accounts`. UI «История изменений» (кто/что/когда) в shared workspace.

**7.4 Регистрация (architecture #6):** к авто-провизионингу — `users`: `display_name`,
`email` (на случай потери Telegram), `consent_at` (согласие на обработку). Экран
дозаполнения при первом входе.

**7.5 Удаление (architecture #7):** soft-archive юзера (30 дней → purge). Personal
workspace архивируется; shared — остаётся у второго (убираем только membership). Без
каскада на shared-данные. **PIN (default, подтвердить — open Q #3):** при soft-delete
`active_workspace_id → NULL`; если юзер логинится в 30-дневном окне — экран «восстановить
аккаунт?» до показа данных, restore = un-archive personal + `active_workspace_id` ← personal.
**Hard-purge под `workspace_id RESTRICT` (pass-2 A3):** soft-archive RESTRICT не трогает,
но purge удаляет **в порядке зависимостей**: дочерние строки (`envelope_entries →
transactions → planned_operations → accounts/categories/budgets/envelopes → audit_log`)
→ personal `workspace` → `user`. Иначе FK-violation. Invite-FK на юзера — `SET NULL`.

**Тесты:** invite happy + cap-3→409 + expired/revoked, shared-workspace оба видят tx,
audit пишет actor, удаление юзера не трогает shared workspace второго, cross-workspace
после accept.

**Commits:** invites, shared+switch, audit_log, registration fields, soft-delete. Deploy.
