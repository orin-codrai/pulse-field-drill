## 0. Контекст и смена цели

- Sprint 3a backend закрыт (7-таблица схема, accounts/categories/transactions CRUD, balances, провизионинг, deploy на VPS).
- Phase 1 backend bodies (goals/budgets/reports) и Phase 2 минимальный frontend задеплоены и работают в Telegram.
- Проведён dogfood: **2 дня реального использования вдвоём с партнёром**. Это дало ключевые продуктовые выводы (ниже).
- **Цель проекта уточнена:** довести финтрекер до состояния «пригоден для личного использования» (v1.0), закрыть галку, вернуться к основному продукту Pulse (B2B для селлеров маркетплейсов).

**Важно про природу проекта:** это **pet-проект для личного использования** (я + партнёр). Это **НЕ продукт для рынка**. Поэтому:
- Регуляторика / лицензии / инвест-советы — **не применимы** (управляю своими деньгами с собственного согласия).
- Не нужен customer research, анализ ЦА, подстройка под сегменты.
- Решения принимаются по принципу «удобно мне и партнёру», не «масштабируемо для рынка».

## 1. Главные выводы из dogfood (в порядке важности)

1. **Планирование важнее аналитики.** Главное чего не хватает — модуль планирования будущих трат по датам с прогнозом баланса. Аналитика (которая была в Phase 3) оказалась не нужна — в списке транзакций всё и так видно.
2. **Нужен multi-user.** Тестировали вдвоём, сразу выяснилось что нужен совместный учёт.
3. **Pay-yourself-first конверты.** Нужно «прятать» часть дохода в конверты с настраиваемым % (НЗ, отпуск и т.д.), опираясь на методологию книги «Самый богатый человек в Вавилоне».
4. **Дизайн отталкивает.** Текущий UI выглядит generic AI-generated, вызывает отторжение. Нужен полный design-рефреш.
5. **Подкатегории.** Планирование требует более тонкой детализации трат.

## 2. v1.0 Done Criteria (галка — когда проект готов для личного использования)

Галка закрыта когда **ВСЕ** пункты выполнены:

1. **Совместный аккаунт.** Партнёр принимает приглашение (отправленное изнутри приложения), оба видят общие транзакции на совместном аккаунте, видна история изменений (кто / что / когда).

2. **Добавить трату ≤ 3 тапа.** Дефолтный счёт подставляется автоматически (последний использованный), смена счёта — опциональный 4-й тап, не обязательный. Проверка: засечь реальное добавление, посчитать тапы.

3. **Модуль планирования.** Внести будущую трату {сумма, дата, периодичность, счёт-источник}. Прогноз показывает «к концу месяца останется N» с учётом запланированного. Проверка сценарием: «квартира 35000 ежемесячно с 1 числа» → видна в прогнозе, прогноз пересчитан.

4. **Pay-yourself-first конверты.** Создать несколько конвертов со своими процентами (НЗ 10%, отпуск 15%, и т.д., % задаёт юзер сам). При внесении дохода конверты автоматически отщипывают свою долю **виртуально** (см. архитектурное решение ниже). Видно накопленное в каждом конверте + «доступно к трате» за вычетом конвертов.

5. **Дизайн — не AI-generated (критерий через процесс, не через ощущение):**
   - создан `docs/design-tokens.md` (палитра, типографика, spacing, радиусы, icon-политика)
   - ключевые страницы (Балансы, Добавление транзакции, Планирование) перерисованы по токенам
   - эмодзи-иконки заменены на единый SVG icon-set (Lucide / Phosphor / Tabler)
   - проверено в светлой И тёмной теме Telegram
   - финальная проверка: рядом со скриншотом референса (топовое финансовое приложение) разница в полировке не бросается в глаза

6. **FINAL GATE: 2 недели реального использования.** После закрытия пунктов 1-5 стартует отсчёт. Пользуюсь ежедневно вместо любой альтернативы 14 дней подряд. Если бросил раньше — понять почему, починить, рестарт отсчёта.

## 3. Архитектурные решения (ЗАФИКСИРОВАНЫ — не пересматривать)

1. **Конверты виртуальные.** Деньги физически НЕ двигаются между счетами. Конверт = помеченная (зарезервированная) часть баланса счёта, которая вычитается из «доступно к трате» и скрыта из основного обзора баланса. Реальное движение денег = не для v1. Главное — «спрятать от изначального взора», чтобы психологически деньги воспринимались как недоступные.

2. **Multi-user модель:**
   - Совместный аккаунт — отдельная сущность, которую можно выбрать в настройках (наряду с личным).
   - Приглашение второго человека — изнутри приложения (не QR, не ручной tg_id).
   - Оба участника имеют полные (root) права на совместном аккаунте.
   - Видна история изменений (кто/что/когда менял).
   - **Без каскадных зависимостей при удалении:** если один удаляет аккаунт — удаляет только на своей стороне, совместные данные остаются у второго.
   - v1: максимум 2 участника. (Бизнес-сценарий с админкой и выдачей прав — держать в голове на будущее, но НЕ для v1.)

3. **Модуль планирования — новая сущность** (не переиспользование budgets/goals). Минимальная модель: запланированная операция = {сумма, дата, категория, счёт-источник, периодичность (разово / неделя / месяц / год), количество циклов, статус (запланирована / подтверждена / отклонена)}.

4. **Когда дата плана наступает** → уведомление «подтвердить?» → подтверждение создаёт реальную транзакцию. (Автоисполнение агентом — НЕ для v1.)

5. **Подкатегории — создаёт юзер сам** (системные категории без принудительных подкатегорий). v1: глубина 2 уровня (категория → подкатегория). Третий уровень — в backlog, добавить только если в использовании окажется что двух мало.

6. **Регистрация:** добавить к текущему авто-провизионингу из initData — имя/прозвище отдельно от Telegram, email (на случай потери Telegram), согласие на обработку данных.

7. **Удаление аккаунта:** архивирование с возможностью восстановления в течение 30 дней, затем полное удаление. Совместные счета остаются у не-удалившихся участников.

## 4. Решения, которые нужно ПРИНЯТЬ при переписывании плана

> Эти вопросы не решены — Claude Code должен предложить решение с обоснованием.

1. **Конверты vs Goals — одна сущность или две?**
   Конверт «отпуск 15%» по смыслу = цель накопления (goal) с автопополнением по проценту. Похоже, они дублируют друг друга. **Рекомендация автора фидбека:** объединить в одну сущность «конверт/цель» с опциональными полями (% автопополнения, целевая сумма, целевая дата). Если так — отдельная таблица `goals` из Sprint 3a либо переосмысляется, либо мигрируется. Claude Code: оцени, предложи модель, учти что в БД уже есть таблица `goals`.

2. **Budgets в v1 или в backlog?**
   Budgets (лимиты трат на категорию) — это НЕ то же что конверты (резервирование дохода). В done-criteria budgets не упомянуты. Похоже, их можно убрать из v1 (UI к ним не делать), backend-стаб оставить. Claude Code: подтверди или оспорь.

3. **Прогноз баланса — алгоритм.**
   «К концу месяца останется N» = текущий баланс + запланированные доходы − запланированные траты до конца периода. Нужно определить: учитывать ли в прогнозе конверты (зарезервированные деньги)? Скорее всего «доступно к трате» = баланс − конверты − запланированные траты. Claude Code: предложи точную формулу.

4. **Совместный аккаунт — модель данных.**
   Как технически связать двух users с одним «совместным» набором счетов/транзакций? Варианты: (а) поле `shared_account_group_id` на счетах, (б) отдельная сущность «household» с membership-таблицей. Claude Code: предложи модель с учётом «без каскадного удаления».

## 5. Feature spec по модулям (детали из dogfood)

### Планирование
- Внести будущую трату с датой, периодичностью, количеством циклов, счётом списания.
- Возможно (позже) — детализация куда именно, чтобы агент в будущем сам создавал транзакции (НЕ v1).
- Вид: список «что предстоит» отсортированный по датам + прогноз баланса. Календарный вид — опционально.
- Прогноз с корреляцией к истории использования (типовые траты как «продукты ~20000/мес») — упрощённо для v1, можно по средним за прошлые месяцы.
- Психологический акцент (важный инсайт из dogfood): если после планов «почти ничего не остаётся» — НЕ показывать голую правду в лоб, а переформулировать в «вот излишек N, подумай куда направить». Видеть «осталось 2000» демотивирует; видеть «есть излишек, распредели» — мотивирует.

### Конверты (pay-yourself-first)
- Юзер создаёт несколько конвертов со своими % (НЗ 10%, отпуск 15%, непредвиденные N%).
- При подтверждённом доходе конверты автоматически отщипывают долю (виртуально).
- Накопленное видно по каждому конверту.
- «Доступно к трате» = баланс − сумма конвертов.
- Превышение лимита конверта — пока просто визуальный сигнал (модуль «гневных/мотивирующих уведомлений от агента» — в backlog, НЕ v1).
- Жёсткая блокировка vs мягкое предупреждение — для v1 мягкое (просто прячем из обзора), режимы — backlog.

### Multi-user
- См. архитектурное решение №2.

### Подкатегории
- Юзер создаёт сам, 2 уровня в v1.
- Пример: Продукты → Овощи / Мясо / Молочка.

### Регистрация / удаление
- См. архитектурные решения №6, №7.

### Дизайн
- Цель: не выглядеть AI-generated, вызывать удовольствие при ежедневном использовании.
- Подход: **взять стилистику любого топового open-source финансового приложения** как референс и адаптировать. Глубокий анализ ЦА и подстройка цветов под сегменты — НЕ нужны (pet-проект под себя).
- Обязательно: изучить `/mnt/skills/public/frontend-design/SKILL.md` перед редизайном.
- Процесс: design-tokens.md → перерисовка по одной странице → скриншот → итерация. Не всё разом.

- Phase 5: multi-user (совместный аккаунт) + регистрация/удаление
- Phase 6: дизайн-рефреш (design-tokens + перерисовка ключевых экранов)

## 7. НЕ входит в v1 (явный backlog — зафиксировать, не реализовывать)

- Агент сам исполняет транзакции (v1 = только уведомление «подтвердить?»)
- Агент решает где выгоднее держать буфер / инвест-советы
- Реальное движение денег между конвертами/буферами
- Модуль «гневных/мотивирующих уведомлений» от персоны агента
- Цепочки уведомлений
- Подкатегории 3-го уровня
- Аналитика / отчёты UI
- Budgets UI (если решено убрать из v1)
- Режимы жёсткой блокировки конвертов
- Мультиюзер 3+ человек с админкой и ролями (бизнес-сценарий)
