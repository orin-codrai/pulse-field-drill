# ADR 0002 — Структура: моно-репо

- **Status:** Accepted
- **Date:** 2026-05-13
- **Deciders:** @orrin

## Контекст

Проект состоит как минимум из трёх артефактов: backend (FastAPI),
frontend (React Mini App) и infra (compose, Caddy, cron, runbook).
Нужно решить — один репозиторий или несколько.

Контекст соло-разработчика: ~несколько часов в неделю, нет CI-команды,
нет отдельных релизных циклов между слоями.

## Рассмотренные варианты

### Моно-репо ✅ выбрано

```
pulse/
├── backend/
├── frontend/
├── infra/
└── docs/
```

**За:**
- Один `docker-compose.yml` собирает всё локально.
- Один CI-pipeline в GitHub Actions.
- Атомарные коммиты «фронт+бэк» — рефакторинг API не разрывается.
- Меньше когнитивной нагрузки на соло-разработчика.

**Против:**
- При желании отдать только backend в опен-сорс пришлось бы разделять —
  не наш случай, AGPLv3 покрывает весь проект.

### Multi-repo (app + infra отдельно)

**За:**
- Чище разделение слоёв.
- Infra можно было бы потом переиспользовать в Pulse.

**Против (решающее):**
- У Pulse будет **свой** infra-репо. Делать «общий infra-репо» для двух
  проектов — преждевременная абстракция (см. CLAUDE.md: «no premature abstractions»).
- Удвоенный overhead на синхронизацию версий между app и infra.
- Соло-разработчику с 2–3 часами в неделю — лишний контекст-свитчинг.

## Решение

**Моно-репо.** Соло-разработка + единый деплоймент-юнит + отсутствие
независимых релизов = классический случай для моно-репо.

## Последствия

- Все артефакты идут одним коммитом, одной версией.
- `gh repo create pulse --public --license=AGPL-3.0`.
- При переходе на Pulse этот репозиторий **не** переиспользуется как
  infra-основа. Он остаётся учебной площадкой; Pulse получает свой репо
  и свой infra-репо.
