# ADR 0004 — Event-sourced балансы

- **Status:** Accepted (backfill — решение принято и в коде с Sprint 3a)
- **Date:** 2026-05-28 (документировано задним числом)
- **Deciders:** @orrin

## Контекст

Баланс счёта нужен в нескольких местах (обзор, прогресс цели/конверта, прогноз).
Вопрос: хранить ли `balance_minor` как материализованную колонку на `accounts`,
обновляя её на каждой транзакции, или вычислять on-read из транзакций.

## Рассмотренные варианты

### Event-sourced — вычисление on-read ✅ выбрано

`balance = initial_balance_minor + Σ(in) − Σ(out)`, где in/out определяются по
`kind` и `from/to_account_id`. Один SQL с `CASE`/`JOIN`, без N+1
(`app/services/balances.py`).

- Источник истины — неизменяемый журнал транзакций. Баланс нельзя «рассинхронить».
- Нет конкурентного UPDATE одной строки `accounts` → нет lost-update под параллельной записью.
- Корректировки/удаления автоматически отражаются в балансе.

### Материализованная колонка `balance_minor`

- Быстрее на чтение, но требует транзакционного UPDATE на каждый insert/delete tx.
- Риск дрейфа: любой путь записи мимо хука ломает инвариант; нужна сверка/пересчёт.
- Lost-update под конкуренцией без блокировок.

## Решение

Балансы — event-sourced. Колонки `balance_minor` нет. `accounts.initial_balance_minor`
— стартовая точка, дальше всё из `transactions`. XOR-CHECK на `transactions`
(`transactions_kind_fields_chk`) гарантирует, что каждая строка имеет корректный
набор FK, поэтому in/out-семантика join'а однозначна (в т.ч. для `adjustment` с
ровно одним non-null FK).

## Последствия

- На объёмах соло-юзера (тысячи tx) on-read агрегация дешевле любых проблем дрейфа.
- Тот же принцип распространяется на **конверты** ([ADR-0007](./0007-envelopes.md)):
  `reserved` конверта = Σ `envelope_entries`, без материализованной колонки.
- Если когда-нибудь упрётся в производительность — materialized view с периодическим
  refresh, не ручная колонка. Пока не нужно.
