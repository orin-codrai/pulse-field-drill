# ADR 0006 — Миграции через Dockerfile CMD, не в FastAPI lifespan

- **Status:** Accepted (backfill — решение принято и в коде с Sprint 3a)
- **Date:** 2026-05-28 (документировано задним числом)
- **Deciders:** @orrin

## Контекст

Alembic-миграции должны прогоняться до старта приложения на каждом деплое. Вопрос:
запускать их из FastAPI `lifespan` (на старте процесса) или отдельным шагом в
Dockerfile `CMD` перед `uvicorn`.

## Рассмотренные варианты

### `CMD ["sh","-c","alembic upgrade head && uvicorn ..."]` ✅ выбрано

Миграции прогоняются shell-шагом до запуска ASGI-сервера, в отдельном (синхронном)
процессе alembic.

- Нет конфликта event loop'ов.
- `&&` гарантирует: не стартуем сервер, если миграция упала (fail-fast на деплое).
- Логи миграции отделены от логов приложения.

### `command.upgrade(...)` из async `lifespan`

- **Детерминированно вешает event loop** при async-движке: alembic запускает свой
  `asyncio.run()`/создаёт вложенный loop поверх уже работающего uvicorn-loop'a
  (alembic issue #1483, #1722). Splash без явной ошибки, процесс висит.
- Смешивает обязанности: бизнес-процесс не должен делать DDL на старте.

## Решение

Миграции — шагом `alembic upgrade head` в Dockerfile `CMD`, затем `uvicorn`.
`Dockerfile` копирует `alembic/` + `alembic.ini` в образ.

## Последствия

- На каждом `docker compose up -d --build` контейнер сам себя мигрирует до готовности.
- Откат — отдельная ручная команда (`alembic downgrade`), не автоматизируется в CMD.
- Для тяжёлых/долгих миграций под нагрузкой (не наш кейс — соло) нужна была бы
  отдельная стратегия (миграция как job, blue-green). Пока fail-fast достаточно.
